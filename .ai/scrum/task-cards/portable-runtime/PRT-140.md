# PRT-140 — Select chevron parity across Designer, Form and Viewer

## Objective

Characterize the `select` schema chevron on the three UI surfaces and restore the
behavior its own contract describes.

## Product boundary

SISAD-PDFME reusable. No concrete consumer business semantics.

## Characterized divergence

The condition read `shouldShowChevron = mode !== 'form'` while the comment above it
stated the chevron is *"shown in every UI mode so the field always reads as a
dropdown"*. The two contradicted each other, and the code hid the chevron precisely on
the surface where the user opens the dropdown.

Two facts confirm it is a regression, not a decision:

- the previous condition was `mode !== 'pdf'`, and `Mode` is `'viewer' | 'form' |
  'designer'` — there is no `'pdf'` member, so the original expression was always true
  and the chevron rendered on all three surfaces;
- the container still reserves `padding-right: 22px` **only** in form mode, exactly the
  chevron width, which left a permanent empty gutter next to every select.

The rule that *is* mode-specific is a different one: the interactive native `<select>`
overlay must mount only in form, because in designer it would capture pointer events
and block drag, selection and Moveable.

## Decision

The chevron is decorative (`pointer-events: none`) and renders on all three UI
surfaces; `ui` never runs during PDF generation, so there is no mode to exclude. The
width and the reserved gutter now come from a single `CHEVRON_SLOT_PX` constant, so
they cannot drift apart again. The native overlay keeps its `mode === 'form' &&
!schema.readOnly` guard.

## Acceptance

- [x] characterization test covering Designer, Form and Viewer;
- [x] chevron present on the three surfaces, including read-only fields;
- [x] chevron never captures pointer events;
- [x] native `<select>` still exclusive to form;
- [x] reserved gutter and chevron width share one source.
