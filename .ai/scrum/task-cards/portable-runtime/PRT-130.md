# PRT-130 — Render SVG schemas into the PDF

## Objective

Replace the reflective `page.drawSvg` probe with a real renderer built on the PDF API
that actually exists, so an `svg` schema appears in the generated document instead of
silently disappearing.

## Product boundary

SISAD-PDFME reusable. No concrete consumer business semantics.

## Characterized divergence

`pdf-lib@1.17.1` does not implement `PDFPage.drawSvg`. Its drawing surface is
`drawText, drawImage, drawPage, drawSvgPath, drawLine, drawRectangle, drawSquare,
drawEllipse, drawCircle` — verified against the installed package. The plugin probed
for `drawSvg` at runtime and returned when absent, so every `svg` schema was a no-op:
the PDF generated without the graphic and without any error.

An interim replacement extracted `<path d>` with a regular expression and scaled by a
hardcoded `488/600` — the dimensions of the plugin's own default icon. That renders any
other SVG at the wrong size and ignores `viewBox`, nested `transform` and paint
inheritance.

## Decision

`drawSvgPath` is the real capability: it draws one path in raw SVG coordinates and
always concatenates `translate(x,y) rotate scale(1,-1)`. The renderer therefore emits,
per shape, its own CTM pre-multiplied by that same flip, so the composed matrix is
exactly the intended SVG→PDF mapping.

Supported subset: `svg`, `g`, `path`, `rect`, `line`, `polyline`, `polygon`, `circle`,
`ellipse`; `viewBox` / `width` / `height`; `preserveAspectRatio` `meet` and `none`;
`transform` (`matrix`, `translate`, `scale`, `rotate`, `skewX`, `skewY`); inherited
`fill`, `stroke`, `stroke-width`, `opacity`, `fill-opacity`, `stroke-opacity`, and the
`style` attribute. Anything else raises `SvgRenderError`.

## Acceptance

- [x] no reflective probe and no silent no-op;
- [x] the real PDF API is characterized and used;
- [x] the drawing respects the schema box, `viewBox` and nested transforms;
- [x] an undrawable document fails loudly;
- [x] a PDF test proves the geometry reaches the page.

## Export classification

- `SvgRenderError` — **PUBLIC_API**. A host generating PDFs from templates of unknown
  origin needs to tell an unsupported SVG apart from any other generation failure.
  Exported from `@sisad-pdfme/schemas`, which is a knip entrypoint.
- `planSvgDraw`, `parseSvgTransform`, `buildSvgViewportMatrix`, `svgShapeToPathData`,
  `multiplySvgMatrix`, `toDrawSvgPathMatrix`, `buildPivotRotationMatrix`,
  `parseSvgViewBox`, `parseSvgLength`, `IDENTITY_MATRIX`, `SVG_SHAPE_TAGS` — **INTERNAL**
  to the renderer pair, consumed across the two modules.
- `parseSvgMarkup`, `parseSvgNumberList` — **INTERNAL**, single-module; not exported.
- applying a matrix to a point was **TEST_ONLY** and lives in the test, not the source.

## Evidence

Source:

  draw plan, `SvgRenderError`;

  `pushGraphicsState` / `concatTransformationMatrix` / `drawSvgPath`.

Executed:

- `npx vitest run tests/unit/sisad-pdfme-comprehensive/contracts/schemas/svgPdfRendering.test.ts`
  → 16 passed. Asserts geometry operators (`cm`, `m`/`l`, `f`, `rg`) in the content
  stream of the saved-and-reloaded PDF, the viewBox→box mapping, the composition of a
  group `transform`, paint inheritance, and five fail-closed paths.
- `npx tsc --noEmit` → clean.

## Known limits

`fill-rule="evenodd"`, `<text>`, `<image>`, `<use>`, `<defs>`, `<style>`, gradients,
clip paths and masks are rejected rather than approximated. Widening the subset is a
new slice, not a silent fallback.
