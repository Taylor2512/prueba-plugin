# TRC-014 — Canonical config pipeline: InputConfig vs ResolvedConfig

## Objective

Codify existing canonical config compiler pipeline and portable persistence boundaries.

## Required pipeline

Host InputConfig -> validate -> normalize -> compile -> ResolvedConfig(revision, hash, capabilities, immutable effective config)

## Acceptance

- pipeline documented and test-backed as existing authority;
- portable template stores declarative config only, not full runtime resolved object;
- non-portable entities rejected from persistence.

## Rejected persistence

functions, plugin implementations, React nodes, DOM refs, HTTP clients, callbacks, providers, AbortControllers.

## Safety

Do not introduce second config manager.

## Evidence executed — 2026-08-18 (PARTIAL)

- Canonical pipeline already active in source:
	- `normalizeSisadPdfmeConfig`
	- `resolveSisadPdfmeConfig`
	- `compileSisadPdfmeConfig`
	- semantic `hash` + monotonic `revision` + deep freeze.
- Focal tests executed:
	- `tests/unit/contracts/config/configCompiler.test.ts` PASS (11/11)
	- `tests/unit/contracts/config/configEffectPlan.test.ts` PASS (6/6)

### Why PARTIAL

- Portable template persistence boundary for declarative config is only partially enforced in template preflight.
- Full rejection matrix for non-portable config entities in import/export path remains to complete with TRC-017/TRC-018/TRC-045.
